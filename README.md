# ITK Dev Tech Radar

How ITK Dev rates the technologies we build with: what we adopt, trial, assess
and hold, and why.

> **Live site:** <https://itk-dev.github.io/itk-tech-radar/>

Inspired by the [Thoughtworks Technology Radar](https://www.thoughtworks.com/radar),
built with [Astro](https://astro.build) and styled with the
[ITK Aarhus design system](https://itk-dev.github.io/itkaarhus-design-system/).

## Local development

The site runs in Docker behind the ITK Dev Traefik setup
([devops_itkdev-docker](https://github.com/itk-dev/devops_itkdev-docker)), with
[Task](https://taskfile.dev/) for the everyday commands:

```sh
task start    # dev server with hot reload
task open     # http://itk-tech-radar.local.itkdev.dk/itk-tech-radar/
task logs     # follow the dev server log
task stop
task check    # everything CI checks: content, types, build, coding standards
task          # list all tasks
```

The first `task start` installs dependencies in the container, so give it a
moment and follow along with `task logs`. Fix formatting with
`task coding-standards:apply`.

Without Docker, the same commands are npm scripts on Node.js 22.12 or later:
`npm install`, then `npm run dev` (<http://localhost:4321/itk-tech-radar/>),
`npm run build` and `npm run format`.

`dev` and `build` first run `npm run sync:design-system`, which downloads the
design system payload into `vendor/` (git-ignored). See
[Design system](#design-system).

## Content

Agents (and people who want the full detail) should read
[`AGENTS.md`](AGENTS.md): the content rules, recipes for every kind of change,
and how blips are written.

| Path | What it holds |
| --- | --- |
| `src/content/blips/*.md` | One file per blip: frontmatter plus the write-up |
| `docs/blip-template.md` | Annotated template for a new blip |
| `src/data/radar.ts` | Quadrants, rings and editions |
| `src/data/evidence.json` | Usage figures, generated by `npm run evidence` |
| `src/content.config.ts` | The blip schema; the build fails on invalid frontmatter |

### Blip frontmatter

```yaml
---
title: Rector
summary: One sentence, shown in lists and as the page description.
quadrant: tools            # languages-and-frameworks | tools | platforms-and-infrastructure | techniques
champion: Jane Doe         # optional
tags: [php, upgrades]
links:
  - label: getrector.com
    url: https://getrector.com/
evidence:                  # optional; how `npm run evidence` finds it
  description: Configures or requires Rector
  composer: [rector/rector]
  files: [rector.php]
history:                   # oldest first
  - edition: '2026.1'
    ring: trial            # adopt | trial | assess | hold
    note: Why it is in this ring in this edition.
---
```

The body is the write-up: what it is, how we use it, and why it sits in its
ring. Link to other blips with relative links, e.g. `[PHPStan](../phpstan/)`;
the build fails on links to blips that do not exist.

The ring comes from the `history` entry for the current edition. A blip without
one is not on the current radar, but its file and history are kept. Blip
numbers are assigned at build time (quadrant, then ring, then title), and
positions are computed deterministically, so there is nothing to place by hand.

## Publishing a new edition

1. Add the edition to `editions` in `src/data/radar.ts`, e.g.
   `{ id: '2027.1', published: '2027-05' }`.
2. Add a `history` entry for the new edition to every blip that stays on the
   radar, with the ring and a note. Add new blips; leave out blips that drop
   off. New and moved blips get their markers automatically.
3. Refresh the usage figures with `task evidence` and commit the result.
4. Merge to `main` through a pull request, with the edition in
   `CHANGELOG.md`.
5. Release it (below). A new edition is a minor release.

## Releasing

Releases use bare semver tags (`1.0.0`, no `v`), as in our other repositories.
The edition id (`2026.1`) is part of the content and is separate from the
release version. Minor releases ship a new edition or new features; patch
releases fix content or code within an edition.

1. On a `release/<version>` branch from `main`, roll `CHANGELOG.md`
   `[Unreleased]` into `[<version>] - <date>`, set `version` in `package.json`,
   and open a pull request (`chore: release <version>`).
2. After it is merged, tag `main` and push the tag. This triggers the deploy:

   ```sh
   git checkout main && git pull --ff-only
   git tag 1.0.0
   git push origin 1.0.0
   ```

Merging to `main` does not deploy. The `github-pages` environment must allow
tag deployments: under **Settings → Environments → github-pages → Deployment
branches and tags**, add a tag rule matching `*.*.*`. Without it, the tagged
deploy is rejected.

## Usage figures

`task evidence` (or `npm run evidence`) uses the GitHub CLI (`gh auth login`
first) to inspect every public, non-archived, non-fork repository in `itk-dev`
pushed to in the last 18 months (`npm run evidence -- --months N` to change),
and writes `src/data/evidence.json`. The signal for each blip — Composer or npm
packages, root files, patterns in the contents of root files (e.g.
`docker-compose.yml`) or workflow file names — is the `evidence` field in its
frontmatter. The build fails when `evidence.json`
was collected with different rules than the blips have now. Private
repositories are excluded on purpose, because the repository names are
published on the site.

## Design system

The site loads the design system's `tokens.css`, `components.css`, Lucide
sprite and Aarhus Kommune marks. The version is pinned in `package.json` under
`config.designSystemVersion`. The design system ships as a Composer dist
archive, not an npm package, so `scripts/sync-design-system.mjs` downloads the
archive for that tag. The favicon and the footer endorsement lockup are not part
of the archive, so they are fetched from the tagged source tree. To upgrade,
change the version and run `task restart` (or `npm run sync:design-system`).

To try unreleased design system changes against a local checkout (default
`../itkaarhus-design-system`, or set `DESIGN_SYSTEM_DIR`):

```sh
task design-system:local                                  # in Docker
ITKAARHUS_DS_DIR=../itkaarhus-design-system npm run dev   # without Docker
```

`task restart` (or a run without the variable) goes back to the pinned version.

### Light and dark theme

The site uses the design system's opt-in theme: `<html data-theme="auto">`
follows the OS, and the header switch sets `light`, `dark` or `auto` and stores
it under the design system's `itkaarhus-theme` key. All site styles use the
semantic tokens (`--itkaarhus-bg*`, `--itkaarhus-text*`, `--itkaarhus-border*`,
the role tokens), never raw colour steps, so both themes follow from the
tokens. Check new styles in both themes.
